## Modules, identity, and authorization boundary

- Active modules are root `AppModule`, `AuthModule`, `CoreModule`, `OwnerModule`, and `InstitutionOperationsModule`. `AuthModule` configures a five-request/60-second throttler and registers account-session, Owner, Institution Admin, and Institution Staff guards/strategies. `InstitutionOperationsModule` mounts Admin and Staff operations controllers; `AppModule` mounts the public health controller.
- There is no active `@Roles` policy/decorator declaration in `apps/backend/src`. Authorization is enforced by guards: Owner routes use `PlatformOwnerJwtAuthGuard`, which checks current account-session validity, `PLATFORM_OWNER` identity, and a persisted `PlatformOwnerGrant`; unsafe methods also check exact `Origin` and matching CSRF cookie/header ([guard](../../apps/backend/src/common/guards/platform-owner-jwt-auth.guard.ts)).
- `InstitutionAdminJwtAuthGuard` checks `INSTITUTION_ADMIN` identity and current membership, then attaches the server-derived Institution ID. It protects the Institution operations and Staff-management controllers. `InstitutionStaffJwtAuthGuard` checks current `INSTITUTION_STAFF` membership and derives its Institution; operations additionally check current active group assignments. UI `Access` and role-based navigation in `apps/frontend/src/config/permissions.ts` are visibility controls, not API authorization.
- `/auth/me` is protected by `AccountSessionJwtAuthGuard`, then resolves the current identity. The account-session strategy checks the access-token subject/session pairing and current session expiry/revocation; Owner/Admin privileges are then read from current persisted identity/grant/membership state.
- Invitation controllers do not use workspace JWT guards. They use exact-Origin checks and throttling; Admin invitation continuation additionally uses one-purpose cookies and CSRF checks. Staff acceptance uses an email-bound bearer invitation and creates no session.
- Active routes expose Institution-scoped Groups, Student roster, Staff assignments, Institution profile/timezone, and daily Attendance. Student/Guardian self-service, payment, family, and external education workflows remain absent. Shared-schema isolation is represented in source but has not been validated against PostgreSQL under concurrent access.

## Contracts, validation, and inactive source

The active public root `@erp/shared` barrel exports schemas from `auth`, `health`, `institution-admin-onboarding`, `institution-operations`, and `institution-onboarding`; those modules define 81 exported inferred TypeScript type aliases in total. Backend DTOs use the shared Zod schemas and `AppModule` installs global Zod validation/serialization. The shared contract source and active barrel are cataloged in [`data-model.md`](data-model.md).

Business controllers/modules retained in `apps/backend/legacy-reference/` are not imported by the active `AppModule` and are excluded from these routes. The separate active Prisma schema does not contain operational business models for those retained workflows.
