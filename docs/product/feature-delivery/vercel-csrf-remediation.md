## 1. Product discovery

- **Stage status:** complete — scope and priority are user-approved as recorded above.
- **Target users / jobs-to-be-done:** Existing workspace users and people following Owner/Admin/Staff invitation journeys need browser authentication and API requests to work reliably on the confirmed Vercel front-end and back-end origins.
- **Baseline diagnosis (pre-implementation source review, 2026-11-03):** The browser used a separately configured backend API origin with credentialed requests; frontend Vercel config had an SPA fallback only; active `AuthController` had no CSRF-bootstrap `GET`. This identified a source-level transport/bootstrap gap, not an observed production outage or customer impact. The implementation state is recorded in Section 5.
- **Baseline behavior and source links (static source review only):**
  - [`AuthController`](../../../apps/backend/src/auth/auth.controller.ts) defines `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, and authenticated `GET /auth/me`; there is no `GET /auth/csrf`. [`AuthModule`](../../../apps/backend/src/auth/auth.module.ts) registers this controller, and [`main.ts`](../../../apps/backend/src/main.ts) applies the `/v1/api` prefix.
  - [`AuthService`](../../../apps/backend/src/auth/auth.service.ts) returns CSRF tokens in workspace session responses and sets the configured CSRF cookie during authentication/refresh; the cookie is JavaScript-readable, `SameSite=Lax`, path `/`, and secure in production. Refresh cookies are HTTP-only. `AuthController` and the workspace JWT guards validate double-submit CSRF where implemented and compare request Origin with configured `CLIENT_URL`.
  - At baseline, the shared [`auth` schemas](../../../packages/shared/src/schemas/auth.ts) included `csrf_token` in workspace sign-in/session responses but had no standalone response contract for the proposed GET. The standalone contract is now present in source; see Section 5.
  - [`base-query.ts`](../../../apps/frontend/src/api/base-query.ts) defaults `VITE_API_BASE_URL` to `http://localhost:3000/v1/api`, sends `credentials: 'include'`, and reads `erp360_ctk` for `x-csrf-token`. [`owner-invitation-api-slice.ts`](../../../apps/frontend/src/features/owner/owner-invitation-api-slice.ts), [`invitation-client.ts`](../../../apps/frontend/src/features/institution-admin-invitation/invitation-client.ts), [`staff-invitation-client.ts`](../../../apps/frontend/src/features/institution/team/staff-invitation-client.ts), and [`staff-acceptance-client.ts`](../../../apps/frontend/src/features/institution/staff-invitation/staff-acceptance-client.ts) also issue direct requests using `API_BASE_URL`.
  - Admin invitation continuation uses its own `erp360_iac_ctk` cookie and continuation flow in [`invitation-client.ts`](../../../apps/frontend/src/features/institution-admin-invitation/invitation-client.ts) and [`institution-admin-invitation.controller.ts`](../../../apps/backend/src/auth/institution-admin-invitation.controller.ts). The remediation must preserve this separate invitation CSRF context; it must not replace it with the workspace token.
  - At baseline, `apps/frontend/vercel.json` rewrote all paths to `/` for the SPA and had no API proxy route. An intermediate worktree inspection found that baseline config still present; the user then restored the approved configuration as `apps/frontend/vercel.mjs`. The current source rewrite and its limits are recorded in Section 5. [`apps/backend/vercel.json`](../../../apps/backend/vercel.json) remains build configuration only. [`vite.config.ts`](../../../apps/frontend/vite.config.ts) has no development API proxy. [`.env.example`](../../../.env.example) documents the direct local API URL.
- **Approved recommendation and trade-offs:** Use the confirmed frontend origin as the browser-facing API origin, with a path-specific same-origin Vercel rewrite to the confirmed fixed backend origin, ahead of the SPA fallback. Add the approved CSRF bootstrap endpoint. This avoids depending on cross-site browser-cookie behavior while retaining the existing backend-origin and cookie protections. It introduces proxy routing/configuration that must be tested end to end.
- **In scope:**
  1. Workspace authentication and API requests through the same-origin frontend API path.
  2. Owner/Admin/Staff invitation browser flows, including their direct-fetch callers, routed consistently through that path.
  3. Add `GET /v1/api/auth/csrf` (controller route `GET /auth/csrf`) and its response contract/bootstrap behavior.
  4. Preserve distinct workspace and invitation-continuation CSRF tokens, Origin checks, credentials, and existing invitation semantics.
- **Out of scope:** Database/persistence changes; changing account roles or authorization policy; redesigning invitation journeys; changing cookie names or weakening cookie/origin protections; changing either Vercel project settings in this task; accessing production deployments/databases; merge, deployment, or release.
- **Functional outcomes / acceptance criteria:**

  4. Existing exact-Origin validation, backend authorization, and cookie attributes remain intact; no production behavior is claimed until explicitly verified.
  5. The backend, shared contract, and frontend build/lint checks pass; a browser-level check confirms request routing, cookie set/send behavior, and invitation flow behavior in an authorized non-production environment.
