- **Functional outcomes to carry into implementation:** An Owner can issue an invitation for one existing Institution and share its link manually; only a valid, unexpired, unrevoked, unused link can be accepted; acceptance assigns only the fixed Institution Admin role to that exact Institution; any new account is provisioned only in a valid invitation context; an eligible existing account can sign in and accept through the approved continuation flow; a conflicting Institution association is rejected without changing membership; and the Owner has a revoke/replacement path. Owner issuance/status/revoke queries are Institution-scoped. Invitation acceptance begins with unique hash lookup, validates the stored Institution/status/expiry, then reads/creates the Account and membership. No raw bearer, email, or Institution identity should be used as an authorization filter supplied by the browser. Initial volumes are expected to be small; these indexes cover the known lookups. Defer cleanup/retention indexes and query tuning until real volume and retention needs are known.
- **Atomic acceptance, replay, and concurrency recommendation:** In one database transaction, conditionally claim exactly one still-pending, unexpired, unrevoked invitation; reject if the authenticated Account already has any Institution membership or a Platform Owner grant; create the membership using only the invitation's stored `institution_id`; and set acceptance time/account. A conditional state transition whose affected-row count must be exactly one makes replay and concurrent use lose safely. If a new Account is created, create its credential record, membership, accepted-invitation state, and initial shared `Session` row atomically; issue cookies/tokens only after commit. Any uniqueness/FK/eligibility failure must roll back both membership and invitation consumption. Do not treat same-Institution membership as an idempotent success: the approved rule requires the existing account to have no Institution. Concurrent accepts through different invitations for one account are stopped by the membership PK/unique account key. Owner revoke and acceptance must race through the same conditional state transition, so only one terminal transition wins; accepted invitations cannot be revoked into an apparently unused state.
- **Replacement invariant and enforcement:** Recommend at most one currently usable pending first-Admin invitation per Institution. A still-valid link must be revoked before replacement, matching the approved UI. Expired/revoked links may be replaced; issuance should serialize per Institution and refuse a second live pending invite. A partial unique constraint on pending rows can provide a database backstop if supported by the configured Prisma/database workflow; otherwise use a transaction that serializes on the Institution row plus conditional updates and handle serialization/unique conflicts without issuing two live links. Expired pending rows must be excluded by timestamp and can be marked `SUPERSEDED` when replacement is issued. Do not silently rotate a live link during ordinary issue; the explicit revoke/replacement path must make old-link invalidation clear. This is a data-design recommendation for later Security/Architecture review, not a decision about endpoint sequencing.
- **Identity/email binding alternatives:** Recommend **no email binding** for this slice: the bearer is the invitation authority; a new invitee chooses an email and password in the invitation context, while an existing invitee proves account control by signing in. Represent expiry explicitly (including an `EXPIRED` state for replacement bookkeeping); expiry remains authoritative by timestamp. Because a time-dependent `expires_at > now()` predicate is not a suitable partial-index predicate, issuance must atomically transition any expired pending row to `EXPIRED` before creating a replacement; the unique index then blocks two pending rows even under concurrent issuers. Valid links require explicit revoke before replacement. - **Continuation persistence recommendation:** The existing `Session` cannot safely serve as pre-auth invitation continuation: it requires an `Account`, stores a refresh-token hash, lasts seven days, and participates in the Owner-only login/refresh flow. A signed stateless continuation cookie avoids a table but cannot be immediately revoked or rotated/consumed reliably without adding server-side state. Adding a single continuation hash to the invitation row conflates the seven-day invitation with browser-flow state and arbitrarily limits concurrent/restarted flows. Recommend a separate, short-lived `InstitutionAdminInvitationContinuation` row; do **not** add continuation fields to `InstitutionAdminMembership` or overload the invitation bearer hash.
  - Proposed minimal fields: generated `id`; required `invitation_id`; unique `credential_hash` for a second, independently generated opaque secret; optional `account_id` bound after successful identity authentication; `csrf_token_hash`; `created_at`, `expires_at`, nullable `revoked_at`, and nullable `consumed_at`. The dedicated model and only its invitation-acceptance endpoints define the permitted operation; the row is always bound to one invitation and, after sign-in/sign-up, one account. It confers no Owner or Institution authority. Use cascading deletion for these short-lived continuation rows when their invitation/account is deleted, and index `invitation_id` and optional `account_id` for expiry/revocation cleanup. Retain neither raw secret nor raw CSRF token.
  - Set continuation expiry to the earlier of a short configured lifetime (recommend 15 minutes; exact duration remains for implementation planning) and invitation expiry. Do not silently extend it on reload. The original invitation bearer is hashed and is the means to start/restart a flow while the invitation remains pending; successful acceptance is the one-time invitation transition. The continuation credential is reusable only for its narrow flow until expiry, identity binding, revocation, or acceptance—not a one-request token and never a tenant credential. Rotate its stored hash and invalidate the predecessor when binding it to an authenticated account; do not rotate on every request. A resume/bootstrap request rotates the synchronizer CSRF token/hash so a reload can recover without retaining the token in browser storage; it must not extend continuation expiry or grant authority. Logout revokes the active continuation and clears its cookie; if the continuation expires or is lost, the invitee must reopen the original shared link. Invitation revoke/expiry invalidates associated continuations; successful acceptance consumes the winner and invalidates all sibling continuations.
  - Alternatives and trade-offs: invitation-row continuation columns avoid a new table but permit only a single active browser flow and complicate rotation/history; a stateless signed cookie needs a revocation/version store to meet the approved lifecycle and therefore loses its simplicity; extending `Session` with anonymous/pre-auth states couples invitation authority to account sessions and current Owner refresh semantics. A separate continuation table adds one indexed lookup/write per flow and short-lived rows, but separates invitation authority from authenticated sessions and supports concurrent tabs, reload, account binding, revocation, and acceptance races. Expected initial volume is low; define bounded cleanup/retention for expired continuation hashes before release.
- **Continuation and API behavior:** The raw invitation bearer should be placed in a URL fragment rather than path/query where the link format permits; on landing, exchange it in a `POST` body, immediately remove it from browser history with `replaceState`, and never put it in route metadata, Redux/RTK Query state, logs, analytics, error text, or referrers. The exchange validates the unique bearer hash and invitation status/expiry, creates continuation state, and sets only the new continuation secret in an HttpOnly cookie; its JSON response may contain a display-safe Institution label/state and a CSRF token, never either bearer/continuation credential or their hashes. A credentialed resume/bootstrap operation supports reload from the server-side continuation, rotates only CSRF state, returns a fresh CSRF token and safe context, and does not renew expiry or reveal the original bearer. Protect bootstrap with exact-Origin validation and the configured credentialed-origin policy; all subsequent cookie-authenticated mutations require the synchronizer token and exact Origin. If the cookie is gone, restarting requires the original shared link; the UI must communicate that behavior.

After successful existing-account authentication, bind it to that account and rotate the continuation secret. Permit an unassigned session only within a valid invitation continuation; its identity response is `UNASSIGNED`, with no tenant scope. Owner endpoints continue to require the Owner guard; Institution endpoints use a separate guard that re-reads current membership and derives Institution scope from the server-side membership, never a request field or stale role claim. A new-account flow may create `Account`, `Session`, membership, accepted-invitation state, and final Admin identity in one transaction. For an existing eligible account, the unassigned session may predate acceptance, but the acceptance response is not a tenant-authorized identity until commit. In both paths, the acceptance transaction conditionally claims the still-pending/unexpired invitation, confirms account kind is unassigned and no Owner grant or membership exists, creates membership using the invitation's stored Institution, updates account kind and invitation state, and consumes/revokes continuations. Any failure rolls all acceptance writes back; cookies/tenant identity are emitted only after commit. A raced or failed existing-account acceptance leaves no membership and remains non-tenant-authorized.
  - All cross-app request/response and identity schemas belong in `@erp/shared`; keep Prisma-only details and continuation hashes server-side. Add narrow start/resume, invitation-scoped sign-in or account-establishment, Owner issue/revoke/status, and accept contracts without client-selected role, Institution, or redirect. The continuation credential is cookie-only; the raw invitation bearer appears only in the one-time Owner issue response/link and the initial exchange body. Return generic credential/invitation failures and do not offer an email-existence preflight; wrong credentials and ineligible accounts must not distinguish whether an account exists, is an Owner, or belongs to another Institution. The exact endpoint paths/envelopes and compatibility mapping from current `PlatformOwner...` contracts to a server-authoritative identity union remain implementation-plan decisions.
- **Cookie, CSRF, session, and exposure constraints:** The active frontend RTK Query base query already uses `credentials: 'include'` and an `X-CSRF-Token` header; backend CORS permits credentials for an explicit origin list plus `CLIENT_URL`. Current Owner cookies use `SameSite=Lax`; the refresh cookie is HttpOnly and scoped to the auth path, while the readable CSRF double-submit cookie is set by the API host. The deployed frontend/API host relationship is not established by source. Use a host-only HttpOnly continuation cookie, no broad `Domain`, narrow common API path, `Secure` in production, and expiry no later than the server row. `SameSite=Lax` is appropriate only where the frontend/API deployment is same-site; if cross-site, `SameSite=None; Secure` is required and must be paired with exact-origin checks and CSRF controls. Require that header and validate the request Origin for every cookie-authenticated state-changing request; CORS alone is not CSRF protection. Validate Origin on the initial bearer exchange as well. Preserve session revocation checks on every authenticated request/refresh; logout revokes the session and continuation. A revoked/expired account session cannot authorize acceptance, even if a continuation cookie remains.
  - Send `Cache-Control: no-store`; set a restrictive `Referrer-Policy: no-referrer`; avoid third-party scripts/analytics on the invite entry; redact bearer and continuation material from application, proxy, access, error-reporting, and diagnostic logs. ### Session refresh/logout race — Data Contracts design-only follow-up (2026-10-29; user-approved amendment)

- **Stage and authority:** The user separately approved this data/architecture amendment and its implementation-plan addition via the approval form on 2026-10-29. The approval authorizes only the amendment recorded here and in Section 4; it does not mean the backend fix is implemented or the race is resolved. No schema, migration, backend code, generated output, database, or `.env` was changed or accessed in this documentation update.
- **Source evidence:** `packages/db/prisma/schema.prisma` (`Session`, currently `id`, `account_id`, unique `refresh_token_hash`, timestamps, `revoked_at`, and indexes on `account_id`/`expires_at`) and `packages/db/prisma/migrations/20261028210927_platform_owner_identity_session_baseline/migration.sql` have no session-family or successor field. `apps/backend/src/auth/auth.service.ts:89-165` looks up and conditionally revokes only the submitted Session, then creates a successor without lineage. `:167-183` logout updates only the row found by the submitted hash when it is still unrevoked, then returns success regardless of update count. Therefore, if refresh commits first, a later logout with the predecessor hash cannot revoke the successor. `apps/backend/src/auth/auth.service.spec.ts:105-123` covers rejection of an already-revoked refresh token, but has no refresh/logout family-race test. These are source observations; no database state was inspected.
- **Recommended minimum persistence adjustment:** Add required `Session.rotation_family_id String` and a B-tree index on it. Use the first Session's `id` as the family ID: login creates each independent device/session family with `rotation_family_id = id`; every refresh successor inherits the predecessor's family ID. Do not make the family ID unique. This groups only rotations of one login session, so logging out one device does not revoke another device's family.
- **Required serialization/access pattern:** Refresh and logout must use one transaction protocol and one stable family lock. Resolve the submitted refresh-token hash even when its Session is already revoked, obtain its `rotation_family_id`, and lock the family anchor row (`Session.id = rotation_family_id`, e.g. `SELECT ... FOR UPDATE`). Re-read the submitted Session after acquiring the lock. Refresh must conditionally revoke the submitted active/unexpired row and create its successor in the same transaction with the inherited family ID. Logout must revoke all still-active rows with that family ID, including any successor committed before logout acquires the lock. A lookup/lock on only the submitted row is insufficient when logout holds a predecessor and refresh operates on a different descendant row. Since stale-token logout resolves the family through the submitted token hash, retain predecessor Session rows/hashes while any descendant remains active; deleting an expired ancestor early would make that logout unable to locate the family. If policy requires earlier row deletion, a durable hashed-token-to-family tombstone or different model is needed. Preserve the anchor row until the whole family is eligible for cleanup; cleanup must not delete an anchor independently while descendants remain.
- **Concurrency result:** If logout obtains the family lock first, it revokes the family and refresh re-reads the predecessor as revoked, so no successor is created. If refresh obtains the lock first, it commits the successor; logout then acquires the same family lock and revokes that successor and the predecessor. The refresh HTTP response may have been linearized first, but no family token remains usable after logout completes. Concurrent refreshes of one token serialize; only the first can conditionally revoke it and create a successor. Independent family IDs remain untouched.
- **Alternatives and trade-offs:** (1) A dedicated `SessionFamily` row with a family-level lock/revocation timestamp makes the lock anchor independent of Session-row retention and can make family closure explicit, but adds a table/FK and requires refresh/JWT authorization to check family state; this is the fallback if root-Session retention cannot be guaranteed. (2) A self-referential `replaced_by_session_id` chain can identify descendants but requires recursive traversal, chain retention, cycle/uniqueness rules, and the same race serialization; it is not smaller. (3) Account-wide session revocation is rejected because it disrupts unrelated devices. A single `rotation_family_id` plus a retained root Session is the recommended narrow choice; its root-retention dependency is an explicit trade-off.
- **Migration/backfill and rollout:** Add a new additive migration after the current Slice 3 data migration; do not rewrite applied migration history. Add the field nullable, backfill each existing row as `rotation_family_id = id`, set it `NOT NULL`, and add the B-tree index. This deliberately does not group by `account_id`, so independent devices are not merged. Existing predecessor/successor lineage cannot be reconstructed because current rows have no link; a pre-migration revoked predecessor and its former successor will receive different families. Coordinate cutover so no old backend writer can create an unlinked successor during the migration/deployment window; the new backend must always write/inherit the family field. No actual Session data distribution or database was inspected. The backfill is O(number of retained Session rows), updates/locks the table, and the index adds write/storage cost; assess row volume and migration-lock tolerance before any non-disposable rollout.
- **Rollback/retention:** Before adoption, the column/index may be removed only in a verified disposable environment. After families are used, prefer a forward fix; rolling back to the old refresh/logout behavior reintroduces the race. Keep root Sessions and revoked predecessor token-hash rows until all family members are expired/revoked and eligible for family-wide cleanup; long-lived refresh families therefore retain rotation history. This extends the existing unresolved Session retention/cleanup policy and has storage/privacy implications. If the approved retention policy requires deleting predecessor rows sooner, revisit the model before implementation. Do not revoke all account sessions as a migration workaround.
- **Test implications:** Add focused Jest coverage for login family initialization, successor inheritance, logout resolving a revoked predecessor, logout revoking a successor committed first, logout winning before refresh (no successor), two concurrent refreshes from one token (one rotation), rollback if successor creation fails, and preservation of another family on the same account. Add PostgreSQL concurrency/invariant cases to the separately approved narrowly scoped integration harness, and run them only against a positively identified new disposable database. None of these tests or database operations was run in this design review.
- **User decision recorded (2026-10-29):** Approved indexed `Session.rotation_family_id`; each login starts a family using the initial Session ID as its anchor; each refresh successor inherits that family ID; logout revokes only active Sessions in that family. At migration cutover, revoke currently active refresh sessions and require sign-in again because existing predecessor/successor lineage cannot be reconstructed. This is a separate approval from the original Slice 3 plan and is now incorporated into Section 4. The code-review race issue remains open until the backend fix and tests pass.
