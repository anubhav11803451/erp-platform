### Acceptance criteria for design implementation

1. Slice 2 Owner setup presents the approved LegalEntity-parent/Institution-child hierarchy, supports the initial group plus first Institution setup, and has a clear empty, pending, validation, success, service-error, and permission-denied state.
2. The grouped Owner workspace can represent more than one Institution under one LegalEntity without adding Campus persistence/setup, invitations, staff management, or operational tenant data to Slice 2.
3. There is one role-neutral sign-in entry, with no public self-service account creation or role/workspace selector. This is a later-slice design; current Owner-only authentication behavior is not misrepresented as implemented support for institution users.
4. Account creation is reachable only from a valid invitation context. The invitation design covers loading/validation, valid context, invalid/expired/revoked/used, service failure, existing-account/conflict, and completion states; unresolved account/invite policies remain explicit rather than assumed.
5. After authentication, the approved destination is Platform Owner → platform workspace and institution user → their one Institution workspace, based on trusted session context. Missing/mismatched context is handled without choosing another Institution or falling through to an unauthorized workspace.
6. Navigation visibility is not treated as authorization. The proposed flow does not rely on `permissions.ts` or `role-bac` helpers for Owner/institution identity or access enforcement.
7. The proposal reuses current local components and CSS-variable tokens, works at mobile/tablet/desktop widths, supports keyboard operation and visible focus, and exposes validation/status feedback accessibly.
8. No implementation starts until this revised design and the separate pending Slice 2 data/architecture decisions receive their required explicit approvals.

### Superseded architecture draft — retained for history only

- **Affected frontend, API, shared contracts, persistence, and integrations:** Backend identity/authorization, institution and membership persistence, shared Zod contracts, and Owner/invitation/Admin frontend routes. No email integration.
- **Data/security/privacy/tenancy/operations considerations:** Server derives institution scope from active membership. Platform Owner has a separate platform grant, no institution membership, and no operational tenant-data access. Hash invitation tokens at rest; do not log bearer tokens.
- **Options and trade-offs:** Shared schema with `institution_id` versus per-institution schemas. Shared schema is simpler for MVP and eliminates schema routing and migration workers, at the cost of requiring strict scoped data access and constraints.
- **Recommended design and source evidence:** One shared Prisma schema. `Institution` is the authorization boundary; `LegalEntity` is grouping metadata only. Each account belongs to one Institution. Use one password/session mechanism with distinct platform and institution grants.
